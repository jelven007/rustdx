# K线成交量单位验证：rustdx与eltdx

验证日期：2026-10-24（UTC+8）。rustdx源码基线`408e30e`，社区源码基线eltdx 3.3.0。本轮新增真实7709请求和官方`.day`交叉验证，未修改Rust源码。

**本次沪深股票样本的成交量单位随周期编号变化：日线`9/1`返回手，日线`4/1`及5分钟`0/1`返回股。同周期下，38字节和54字节请求的响应正文完全一致。不能把本库所有K线成交量统一除以100，也不能给所有周期统一乘100转股。**

**两库的默认日线对外量都可按手理解，但路径不同：rustdx默认请求`9/1`，直接输出解码值；eltdx默认请求`4/1`，将股数解码值除以100输出`volume_lots`。** 两条路径有不同的量化误差，并不保证数值逐位相等。eltdx允许直接指定`9/1`，此时它无条件计算的`volume_lots = wire / 100`会再次缩小已经是手的源量。

上述单位结论只覆盖本轮股票和ETF样本、指定周期及服务器。指数另见第5节。

## 2. 两库换算逻辑

| 环节 | rustdx当前实现 | eltdx 3.3.0 |
| --- | --- | --- |
| 默认日线编号 | `9/1` | `4/1` |
| 默认请求长度 | 38字节 | 54字节 |
| 取量字段 | 读取u32，再以i32传给`vol_amount` | 读取u32，传给`get_volume` |
| 数值解码 | compact-float公式 | compact-float公式 |
| 原始解码量 | `KlineData.vol`直接保存解码值 | `volume_wire_value`保存解码值 |
| 手数派生 | 源解码器不额外缩放 | `volume_lots = volume_wire_value / 100`，不判断周期 |
| 转标准股量 | 调用者显式传`VolumeUnit`；Shares不缩放、Lots乘100 | 本报告只核查协议层上述字段 |
| OHLC、成交额 | OHLC差分累计÷1000；成交额数值解码后直接输出 | 相同价格比例，成交额直接解码 |

本轮以两个独立Python函数忠实转写双方固定源码公式，并对每个真实编码字段重放。928条记录的成交量及成交额共1,856个字段，双方数值公式输出全部一致；这证明本次真实样本上的数值解码一致，不表示公式在所有输入上等价。**本轮未安装或执行完整eltdx SDK。**

源码入口：[rustdx K线解码](../../../crates/rustdx-core/src/tcp/stock/kline_request.rs)、[数值公式](../../../crates/rustdx-core/src/tcp/helper.rs)、[周期/标准适配](../../../crates/rustdx-core/src/data/model.rs)、[股/手转换](../../../crates/rustdx-core/src/data.rs)；[eltdx K线](../../testing/evidence/tdx-protocol-20261023/eltdx-3.3.0/crates/eltdx-protocol/src/commands/klines.rs)、[周期/数值公式](../../testing/evidence/tdx-protocol-20261023/eltdx-3.3.0/crates/eltdx-protocol/src/unit.rs)、[请求帧](../../testing/evidence/tdx-protocol-20261023/eltdx-3.3.0/crates/eltdx-protocol/src/frame.rs)。源码SHA-256固定在[来源清单](../../testing/evidence/kline-volume-20261024/provenance.json)。

## 3. 日线单位：同日期、同价格、同金额验证

官方对照使用前轮已下载的`hsjday-20261022.zip`，本次重新核验完整ZIP的SHA-256：

`07aab2f1166a794cebfa380cda058417499c4f74049a5fe36fe029f5c803d400`

仅保存四个选定`.day`成员，总计868,224字节，未重复保存549,908,719字节的完整ZIP。独立以32字节记录`<IIIIIfII>`读取日期、OHLC、成交额、量字段；股票/指数价格按100还原，ETF按1000还原。官方ZIP来源沿用[既有下载及数据库验证证据](../../testing/evidence/round3-real-day-databases.json)，不新编造下载URL。

共同日期的144条日线，四个OHLC字段和成交额均与`.day`**精确相等**。因此量的比例比较建立在同证券、同日期、同原价记录上。

以下列出10月22日的真实数值；38和54字节请求各列一致，只展示一次：

| 证券 | `.day`量 | `9/1`解码量 | `9/1 ×100 − .day` | `4/1`解码量 | `4/1 − .day` |
| --- | ---: | ---: | ---: | ---: | ---: |
| sz000001 | 129,764,875 | 1,297,648 | −75 | 129,764,872 | −3 |
| sh600000 | 62,529,869 | 625,298 | −69 | 62,529,868 | −1 |
| sh510300 | 3,541,978,015 | 35,419,780 | −15 | 3,541,978,112 | +97 |
| sh000001 | 437,691,963 | 4,376,919 | −63 | 437,691,968 | +5 |

股票的`.day`量为股，ETF为基金份额。指数表中的量只表示其`.day`源聚合字段，不能把它命名为某只证券的股数。

全部9个共同交易日的观察误差如下。误差是实际数据差值，不是本报告证明的通用误差上界：

| 证券 | `9/1 ×100 − .day`范围 | `4/1 − .day`范围 |
| --- | ---: | ---: |
| sz000001 | −92至−6 | −4至+2 |
| sh600000 | −99至+1 | −3至+1 |
| sh510300 | −98至+36 | −62至+97 |
| sh000001 | −63至+19 | −16至+11 |

差值量级与源量约100倍的比例差异明确分开。不能用低精度日线的手数乘100承诺恢复`.day`每一股，也不能假设所有`9/1`量都只向下取整。

平安银行10月22日的具体路径：

```text
rustdx默认日线：9/1 → vol = 1,297,648 手
eltdx默认日线：4/1 → wire = 129,764,872 股
                     → volume_lots = 1,297,648.72 手
官方.day：129,764,875 股
```

将rustdx默认日线的`1,297,648`再次除100，得到`12,976.48`，会把手数缩小100倍。问题不在38字节请求本身：38字节请求改用`4/1`同样返回股数。

## 4. 股票和ETF 5分钟量：整日聚合交叉验证

每个股票/ETF都返回10月22日、23日各48根5分钟K线。10月22日存在官方日线对照，其时间标签精确覆盖09:35–11:30及13:05–15:00的5分钟网格：

| 证券 | 48根`0/1`解码量之和 | 官方`.day`量 | 相差 |
| --- | ---: | ---: | ---: |
| sz000001 | 129,764,900 | 129,764,875 | +25股 |
| sh600000 | 62,529,900 | 62,529,869 | +31股 |
| sh510300 | 3,541,977,968 | 3,541,978,015 | −47份 |

这些量无需乘100即可接近日线股/份量。38和54字节返回的96根记录全部相同。10月23日尚无本轮官方ZIP对照，不将其计为独立日线验证。

进一步计算每根股票/ETF分钟线的`成交额 / 解码量`，两种请求共576条、去重后288条记录都落在该根最低价至最高价之间（检查容差0.01元）。这是价格量纲的辅助验证；整日聚合与`.day`对齐提供更直接的量单位证据。

本库5分钟股票K线的`vol`在这些样本中应按股传给标准适配器，即`VolumeUnit::Shares`。若传`VolumeUnit::Lots`，现有适配器会乘100，得到错误股量。eltdx的`0/1`源量除100可以得到相应100股/手模型中的手数。

## 5. 指数不能沿用个股分钟单位结论

上证指数日线的`9/1`与`4/1`保持上述约100倍关系，且OHLC、金额均与官方`.day`一致。但10月22日指数48根5分钟量之和为`7,060,954,172`，`.day`量为`437,691,963`，未能按股/手关系对齐。

另外，96根指数分钟记录的`amount / wire_volume`均约为100（范围100.000003至100.000074）。这与股票分钟量的价格检验不同，提示该字段可能采用不同统计口径；本轮没有取得足以解释其业务含义的厂商证据，**不将其命名为股数或真实成交手数**。

指数分钟量单位、指数聚合成分、其他指数和其他服务器仍待验证。ETF的份额模型也不推广到债券的张数或全部基金。

## 6. 数值解码的独立边界问题

虽然真实样本上双方公式完全一致，合成输入揭示两处差异：

| 编码u32 | rustdx `vol_amount` | eltdx `get_volume` | 原因 |
| --- | ---: | ---: | --- |
| `0x00000000` | 5.877471754111438e−39 | 0 | eltdx显式处理零，rustdx计算基础项 |
| `0x41800000` | 2,056 | 16 | rustdx在高字节≤0x80、负指数分支使用倒数；eltdx按基础量缩放 |

两项现有正数参考编码`1235775464`、`1326643033`的输出分别为`1,379,837`、`2,465,683,712`，双方相同。

这些是独立的**数值解码边界问题**，不能用它们解释本轮周期单位的100倍差异。本报告记录候选修复，不修改公式；修复需另行补充零、低成交量及保留编码的针对性回归。本轮合成边界通过源码转写重放，未宣称在两个完整SDK中执行这些合成输入。

## 7. 现有适配规则与剩余范围

在本次样本范围内，调用者可采用：

| 请求 | 股票源单位 | rustdx标准股量适配 | eltdx `volume_lots`的解释 |
| --- | --- | --- | --- |
| 日线`9/1` | 手 | `Lots`，乘100；保留源量精度损失 | 其无条件除100不适用于已是手的源量 |
| 日线`4/1` | 股 | `Shares`，不缩放 | 除100后为手 |
| 5分钟`0/1` | 股 | `Shares`，不缩放 | 除100后为手 |

`Period::Day`目前发`9`，`Period::Minute5`发`0`；`Period::try_from(4/9)`都会映射为Day。因此仅保存Period，或仅记录opcode `0x052D`，不足以保留源量单位，原始周期编号和明确的源单位都应保留。

本轮结案：指定股票/ETF的日线4与9、5分钟0及两种报文长度关系。剩余范围：1/15/30/60分钟、周/月/季/年、自定义参数、债券、北交所、其他服务器和指数分钟口径。复权请求本轮固定为0，**成交量验证完成不代表复权待验证项完成**。
