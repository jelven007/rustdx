# CI 取消测试与绝对截止时间隔离

日期2026-10-25；基线`bd0dd006ad24d440a983b9ed88c481a65291c256`，
独立CI修复分支`codex/version-fixture-20261025`。状态：本机回归、反向证明及
全包检查已核验，远端交付另验。

## 问题与预期

PR #3首次CI的macOS runner测试失败，既有
`database_process::tests::cancellation_and_deadline_kill_blocked_pipe_and_descendants`
期望取消、实际超时。测试应分别验证截止时间和取消，并证明错误后阻塞管道及
进程组已经回收。

## 复现与根因

原用例在启动子进程前建立100毫秒绝对时限，再创建线程、等待20毫秒后取消。
其结果依赖取消线程能在时限前获得调度。受控地将该等待改成200毫秒后，
连续三次稳定复现`timeout != cancelled`，每次Cargo退出101。

| 假设 | 判断 | 证据 |
| --- | --- | --- |
| 取消信号丢失或进程回收失效 | 排除为本次根因 | 超时先于取消是上下文既定行为；修复用例立即/延迟取消和进程组消失断言通过 |
| 两个终止条件在测试中竞争 | 已确认 | 原100毫秒时限在受控200毫秒调度前耗尽；分离预算后通过，恢复100毫秒后同一回归再失败 |

`OperationContext::remaining`按实际已发生的终止条件返回；错误值从测试建立的
短截止时间进入`Process::request`，并非协议或数据库数据导致。原测试随
`47045cd`引入，PR #3仅修改版本夹具前就已存在。

## 修复与回归

修改仅限`database_process.rs`中的`#[cfg(all(test, unix))]`测试：
先启动shell、准备1MiB输入和临时证据，再进入任务上下文。子进程读一个字节后写
就绪标记，随后等待30秒；取消线程有上限地等待该标记，确认大管道写入已开始。
测试独立覆盖100毫秒截止、立即取消、超过原窗口的200毫秒延迟取消；
取消用例使用10秒测试预算，整体5秒上限仍能发现未终止的30秒子进程。
每个用例继续断言错误分类和进程组消失。

首次修复回归1项通过、耗时0.47秒。只将修复测试的取消预算反转回100毫秒，
延迟用例再次失败并退出101；恢复修复后执行最终检查。生产实现与基线的非测试
前缀字节相同，生产时限、取消优先顺序和回收实现保持已有合同。

最终本机格式、runner全目标/全特性Clippy、全包测试、36项Python、
文档/生命周期及功能分支版本检查共8项通过。runner测试35通过、9忽略、0失败；
外部数据库忽略项不计在线通过。首次全包复验曾在
`control_plane.rs:wal_backup_restore_and_corruption_detection`遇到文件锁不可得；
该备份用例随后独立三次通过，同一完整并行测试命令再次全部通过。
首次失败日志和最终日志分别保留，文件锁冲突未稳定复现且未确认根因，
不宣称本次修复了备份或文件锁实现。
